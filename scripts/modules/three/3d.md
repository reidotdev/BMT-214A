# 3D with three.js

This file arrived with the **three.js module** (`pnpm scaffold` → _Optional
modules_, or `node scripts/setup.mjs --modules-only`). The template ships
without three.js on purpose: most sites never need 3D, and the library is one of
the largest things you can put in a bundle.

What follows is the pattern distilled from a production build on this template —
a scroll-driven gallery where DOM cards ride a sine wave in 3D space and a WebGL
cord weaves between them. Every number here was measured on that project, and
every rule is here because breaking it cost something real.

## When _not_ to reach for 3D

Say no by default. Reach for WebGL only when the 3D **is** the content or the
brand — a product you rotate, a signature motif the whole design is built on.
For decoration, CSS transforms, an SVG, or a compressed video get you most of
the way at a fraction of the cost.

What a 3D feature actually costs:

- **Bundle.** three.js, tree-shaken to a scene of primitives, measured **127 KB
  gzipped (526 KB raw)** on that project — with no `GLTFLoader` and no model
  asset, so that was the whole cost. Add a loader, a model, postprocessing or
  physics and it grows from there. The recipe below is what keeps that weight
  off the main bundle; it does not make it disappear.
- **Frames and battery.** A render loop runs forever unless you stop it, and a
  mid-range phone is not your laptop.
- **Browsers you cannot test in CI.** The template's Playwright job runs
  Chromium only. Safari and Firefox WebGL behaviour — and iOS memory limits —
  stay unverified until someone opens the page on real hardware.
- **Maintenance.** 3D maths that has to agree with a CSS layout is a second
  source of truth. It drifts.

If the answer is still yes, build it like this.

## 1. Import three.js dynamically, inside an effect, in exactly one file

```tsx
"use client";
// src/components/<feature>/<feature>.tsx
import type { Scene } from "./scene"; // type-only: erased, costs nothing

const canvasRef = useRef<HTMLCanvasElement>(null);

// three.js is imported here and nowhere else: dynamically, inside an effect, so
// it is code-split, never server-rendered, and never fetched at all when the
// feature is off (mobile, reduced motion, no JS).
useEffect(() => {
  if (!enabled) return;
  const canvas = canvasRef.current;
  if (!canvas) return;

  let cancelled = false;
  let scene: Scene | null = null;

  import("./scene").then(({ createScene }) => {
    if (cancelled) return; // the effect may have torn down mid-import
    scene = createScene(canvas);
  });

  return () => {
    cancelled = true;
    scene?.dispose();
  };
}, [enabled]);
```

`import * as THREE from "three"` appears **only** inside `./scene.ts` — the
module that dynamic `import()` pulls in. One static import of `three` from a
component that renders on the server is enough to put the whole library in the
main bundle, and nothing will warn you.

`next/dynamic` with `ssr: false` is the equivalent move when the boundary is a
component rather than a plain module. Note that the App Router forbids
`ssr: false` inside a Server Component, so it has to sit in a `"use client"`
file either way.

**Verify it, don't assume it.** On that project, conditional loading was
confirmed against a production build by resource timing — the chunk is requested
on desktop and absent under reduced motion and at the mobile breakpoint. Reading
the source proves nothing; bundlers hoist.

## 2. Gate on client capability, and start `false`

```tsx
/**
 * Off until the client says 3D is appropriate. Starting false means the server
 * renders the plain version, which is also exactly what a no-JS visitor keeps.
 */
const [enabled, setEnabled] = useState(false);

useEffect(() => {
  const decide = () => {
    const wide = window.matchMedia("(min-width: 64rem)").matches;
    const still = window.matchMedia("(prefers-reduced-motion: reduce)").matches;
    setEnabled(wide && !still);
  };
  decide();
  window.addEventListener("resize", decide);
  return () => window.removeEventListener("resize", decide);
}, []);
```

- **Viewport width _and_ `prefers-reduced-motion`**, both re-evaluated on
  resize. A media query read once on mount silently stops being true when the
  visitor rotates a tablet or changes the system setting mid-session — the same
  reason `BackgroundVideo` listens for `change` instead of reading `.matches`
  once.
- **The initial state is `false`, always.** The server has no viewport and no
  motion preference, so the non-enhanced render is the only honest one — and it
  is exactly what a visitor without JS keeps permanently. Starting `true` hands
  reduced-motion visitors a flash of the thing they asked not to see, plus a
  hydration mismatch.
- Add further gates the feature needs (WebGL2 support, `document.hidden`), but
  these two are the floor.

## 3. Content stays DOM; the canvas is an overlay

Text drawn into a canvas is invisible to search engines, screen readers,
find-in-page, translation and text selection. So lay the content out as ordinary
DOM with CSS 3D transforms, and put the canvas over it:

```tsx
<canvas
  ref={canvasRef}
  aria-hidden
  className="pointer-events-none absolute inset-0 h-full w-full"
/>
```

The canvas carries no information, so it is `aria-hidden` and takes no pointer
events. It is an overlay, never a replacement for content.

A canvas sitting _above_ the DOM can still appear to pass _behind_ it: for each
element, draw an invisible quad at that element's 3D position with
`colorWrite: false` and depth writing left on. The quad paints nothing but
claims depth, so fragments behind it fail the depth test and the real HTML shows
through. One canvas, one pass, per-pixel — that is how a WebGL cord weaves
between HTML cards.

That trick only holds while the WebGL camera reproduces the CSS `perspective`
exactly. With the camera at `z = P`, where `P` is the CSS perspective, the
closed form `fov = 2·atan(H / 2P)` (H = stage height) landed the proxies on
their elements with no fudge factor. Derive the CSS value and the camera from
**one** config object: a mismatch does not throw, it just looks subtly wrong
forever.

One layout gotcha that flattens all of it: `overflow` other than `visible`
flattens a 3D rendering context. Clipping and `perspective` must live on
**separate nested elements**, or the scene collapses into a flat pile.

## 4. Nodes duplicated for an infinite loop are added after mount

An endless loop needs copies. Copies must not duplicate content:

- The **server renders the canonical set exactly once** — the real semantic
  list, one node per item. That is what a crawler receives.
- The **client clones after mount** to fill the visible window plus a buffer,
  marking every clone `aria-hidden="true"` and `inert`.
- A clone renders its title through a `decorative` prop that demotes the heading
  to a `<p>`, so the copies never duplicate heading levels either.

Measured on that build: the server emits 6 `<article>`, 6 `<h3>` and no
`<canvas>`; after hydration there are 12 cards and still 6 `<h3>`.

Be precise about the claim. A clone's text _is_ in the DOM after hydration — it
has to be, a clone looks identical to what it copies. What is avoided is
duplicated **headings, tab stops and screen-reader output**, not duplicated text
nodes.

## 5. Vanilla three.js, not React Three Fiber

R3F is the more maintainable default in most projects. It was rejected here, and
the reasoning is recorded so it is not re-litigated by accident:

- The scene is tightly coupled to **DOM measurements** and driven by a GSAP
  timeline that already owns the frame loop. A thin imperative module gives
  exact control over ordering — measure DOM → update uniforms → render — inside
  a single `gsap.ticker` callback, with no reconciliation between a scrubbed
  timeline and React state.
- A scene of under ten objects gives a declarative layer little to buy.
- It is also two more dependencies (`@react-three/fiber`, in practice `drei`
  too) on top of the 127 KB.

If the project later wants drei helpers, R3F can wrap the imperative module
without changing any of the maths.

## Gotchas that cost a day (3D edition)

1. **`THREE.Color` cannot read the design tokens.** Tokens resolve to `lab()` in
   current Chrome, and painting one onto a canvas to convert it hands back
   `color(srgb …)`, which THREE cannot parse either. It does not throw — it
   silently falls back to **white**, which is how a white cord shipped on a
   white background. Fix: never pass colour strings to WebGL. Paint one pixel,
   read the bytes with `getImageData`, and build the colour from sRGB
   components.
2. **THREE reports that as a warning, not an error.** A test harness capturing
   only `console.error` sees nothing at all. Capture both.
3. **Dispose everything on unmount** — renderer, geometries, materials,
   textures — and stop the ticker. React's dev-mode double-invoked effects
   otherwise leak a WebGL context per mount, and browsers cap live contexts at
   around 16, after which new canvases simply stay blank.
4. **Pause the loop when the section leaves the viewport and when
   `document.hidden`.** rAF otherwise runs forever, draining battery to render
   pixels nobody sees.
5. **Allocate nothing per frame.** Reuse vectors and matrices; a
   `new THREE.Vector3()` inside the render loop is garbage-collector pressure at
   60 Hz.
6. **Frame timings from CI are meaningless.** Headless environments render
   through SwiftShader, in software. Measure on a real GPU or don't quote a
   number.

## Before merging a 3D feature

- [ ] `three` imported in exactly one module, dynamically, from an effect
- [ ] production build measured: the chunk loads only when the feature is on
- [ ] nothing fetched under `prefers-reduced-motion`, at the mobile breakpoint,
      or with JS off — and the page is complete without it
- [ ] content text still selectable; canvas `aria-hidden` +
      `pointer-events-none`
- [ ] server HTML has the real item count; clones added after mount,
      `aria-hidden` + `inert`
- [ ] scene disposed on unmount; loop paused when hidden
- [ ] `pnpm verify:template`, `pnpm lint`, `pnpm typecheck`, `pnpm format:check`,
      `pnpm build` and `pnpm test:e2e` all green
- [ ] opened on real hardware, Safari included

## Adding this module by hand

If three.js was skipped at setup and the project needs it now:

```bash
pnpm add three
pnpm add -D @types/three
cp scripts/modules/three/3d.md docs/3d.md
```

That is exactly what `node scripts/setup.mjs --modules-only` does.
